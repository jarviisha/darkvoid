# Implementation Plan: Materialized Ranked Feed — Phase P1 (local-only)

**Branch**: `006-materialized-ranked-feed` | **Date**: 2026-07-24 | **Spec**: [design.md](./design.md) (DRAFT v2, review round 1 settled)
**Input**: Architecture design from `/specs/006-materialized-ranked-feed/design.md` — this feature skipped `spec.md`; the reviewed design doc is the source of truth. Scope here is **P1 only** (§9 of design.md): flip the timeline ZSET score axis from timestamp to packed rank score, add `SetPostsBatch`, bump the Redis key to v2, and drop realtime `rankCandidates` from the timeline hot path. Local scoring only — no codohue Rankings wiring (that is P2).

**Note**: This plan was generated by the `speckit-plan` workflow.

## Summary

Today the prepared timeline materializes membership but not ranking: ZSET scores are `UnixMicro(createdAt)` and every `getFeedFromTimeline` request re-runs the local scorer over hydrated posts. P1 makes the ZSET score a **packed rank score** — `PackTimelineScore(rankScore, createdAt)` packs a 20-bit rank bucket (0.001 resolution) above a 32-bit createdAt-seconds component — so ranking happens only in background writers (fan-out and refresher) and the hot path becomes read → hydrate → reorder-to-ZSET-order → enrich → return. Behavior stays 100% local-scored; the result order a user sees should be materially the same as today, computed cheaper.

Key mechanics, all settled in design review (design.md §4, §5, §11):

- **Score encoding** (§4.1): `bucket<<32 | tsSeconds` with clamping; max ≈ 4.5e15 < 2^53 so int64 ↔ Redis float64 is exact; `TimelinePosition.Score`/cursor `tl_score` stay `int64` — the 005 cursor contract is untouched.
- **Fan-out** (§4.4): new posts write the constant write-time score `RecencyScale + RelationshipBonus` packed with `createdAt`; the ts component keeps newest-first ordering inside the constant-score block (fixes the tie flaw found in review).
- **Overwrite path** (§4.7): new `TimelineStore.SetPostsBatch` (plain ZADD upsert) for the refresher; existing `AddPost`/`AddPostsBatch` keep `NX` so late fan-out events cannot clobber refreshed scores.
- **Migration** (§5): key prefix `feed:tl` → `feed:tl:v2`; old keys die by TTL; in-flight old cursors degrade to "read from top" once — accepted.

## Phase 0: Research

Research is captured in [research.md](./research.md). All open questions were resolved during design review round 1 (2026-07-24, recorded in design.md §11); no NEEDS CLARIFICATION remain for P1. The main decisions:

- **Packed score encoding** `bucket<<32 | tsSeconds` over plain `rank*1e6` (tie block from constant write-time scores), over float ZSET scores (cursor type churn), and over UUIDv7 tie-breaks (DB-wide change).
- **`SetPostsBatch` as a new method** over dropping NX from `AddPostsBatch` (fan-out needs NX to not clobber refreshed scores) and over DEL+rebuild (races concurrent fan-out).
- **Key version bump `feed:tl:v2`** over in-place flush (old/new score ranges overlap numerically; TTL handles cleanup for free) and over a cursor version field (one-time soft degradation accepted per soft-cursor decision).
- **Soft cursor** (Q1) and **additive CF blend** (Q2, P2-relevant) recorded with rationale.
- **Write-time fan-out score = `RecencyScale + RelationshipBonus`** as an explicit constant rather than a fake scorer call.
- **Explicit hot-path reorder**: `GetPostsByIDs` does not preserve order; today `rankCandidates` masks that — the refactor must add a deliberate sort by ZSET entry index.
